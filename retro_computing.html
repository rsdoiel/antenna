MacOS Extensions pack for the Apple Network Server v1.0

2026-10-25, updated: 2026-10-30

By now regular readers of this blog are quite familiar with my affection for the 1996 Apple Network Server, Apple's Unix-through-and-through $10,000+ server that only shipped with, and only officially ran, Harpoon, its unique superset of IBM AIX. An ANS 500, the lower tier of this dorm fridge-sized computer, was the first server I ever personally owned, a nearly-new hand-me-down after Steve Jobs convinced Gil Amelio to cancel the machine and the bookstore's vendor at the University I worked for wouldn't support it anymore. There are several fascinating features present in Harpoon that were never implemented in any other Apple product. Currently I have three, that original ANS 500, this ANS 700 here which I use for testing, and a battery-bombed EVT prototype (a so-called "Shiner ESB" that used to be at Netscape).

The ANS was strongly based on the Power Macintosh 9500 and Apple was known to have demonstrated the ANS with Mac OS during development, but this confused potential buyers, causing the ability to boot Mac OS to be stripped from production systems. While then-CTO Ellen Hancock claimed in 1997 a ROM swap would enable the ANS to boot Mac OS again and Windows NT, these ROMs were believed to be vapourware until a former Apple employee presented a working dump of both the preproduction ROM and the later ANS Mac OS ROM. A prototype Windows NT ROM also emerged from another former employee, though there are pieces missing and booting Windows NT natively on the ANS is still a work in progress (hopefully to be the subject of a future article).

It turned out I had one of the preproduction ROMs myself and didn't realize what it was. Because the later Mac OS ROM was apparently unfinished, it doesn't properly support the L2 cache and consequently runs substantially slower, and it can't boot AIX. The preproduction ROM does boot both operating systems and does support the cache. On the other hand, in MacOS it doesn't support the on-board video or the front Fast Wide SCSI-2 controller, the on-board MACE Ethernet doesn't work there either, and after MacOS first boots, the next restart without zapping the PRAM will come up with a black screen.

The good news is, many of the issues with the preproduction ROM in Mac OS can be fixed or worked around in software. So I've fixed or worked around many of them in software: the MACE Ethernet is fixed, the on-board video is now supported, and the ANS can restart properly back into Mac OS. Plus, because it's the preproduction ROM, you can still boot AIX, thus preserving the entire historical reason for Shiner's existence. Here's the first cut of that software and how it was developed.

Naturally, the first order of business is to get an Apple Network Server and the 1.1.20.1 preproduction ROM (the production ROM is version 1.1.22). I can't help you with the first part, but replica ROMs now exist to cover the second part, and as of this writing Joe's Computer Museum has a few in stock (not affiliated, just a satisfied occasional customer). I tested the original design of these ROM DIMMs, kindly provided by Jeff Walther. Jeff assembled and donated this particular batch to Joe Strosnider, who is selling them and donating the proceeds in turn to the maintenance of the Tinker Different forum, where this whole thing started.

Now that you have the basic hardware, you'll then need to install Mac OS to an external bootable SCSI volume. For this project I use a 25-pin BlueSCSI which connects directly to the ANS' rear SCSI port and runs on termination power. Set up a blank disk image of the desired size to the device's (micro)SD card and rename it to the desired SCSI ID, which for the ANS is typically SCSI ID 2.

If you have another Mac with a SCSI port handy, it's easiest to do the MacOS installation to the external volume with that system. Make sure it installs Mac OS for any supported Mac, especially if you are using a model-specific installer CD; up to Mac OS 9.1 inclusive will boot directly on the ANS, and 9.1 is what I'm using here. 7.6 will work and late versions of System 7.5 might work, but I recommend at least 8.1 or later. If you only have the ANS and/or have no other suitable vintage Mac that can perform the installation, you can do it on the ANS itself with a bit more difficulty. For that you'll need to not only create the blank disk image but additionally include an ISO of a bootable MacOS CD (use ID 0), plus install a Power Mac-compatible PCI video card — I use a Twin Turbo 128MA but any ATI Mac-specific card of the era should also work, such as the Rage Orion.

Finally, unplug the server, unlock and pull open the mainboard drawer, remove the PRAM battery, install the preproduction ROM DIMM, and leave the drawer open and the system completely depowered for at least several minutes while you enjoy the droll prose of this blog post.

Here's the back of my testing ANS 700. The monitor is connected to the 700's video port, the BlueSCSI is plugged into the SCSI connector, and a Farallon standard AAUI-to-twisted pair dongle is attached to the on-board MACE Ethernet AAUI port (Apple's perverse little rework of AUI to avoid confusion with the Mac DA-15 video port).

Technically that should be all you need to run Mac OS or AIX. However, I also have the Twin Turbo video card in slot 1 (where it would usually be in a 9500, the closest hardware relative to the ANS), and as an alternative for the MACE Ethernet I have one of the unobtainium 10Mbit ANS Ethernet PCI cards in slot 6 that I ordered from Apple Austin when they were blowing out leftover Shiner hardware. This card works in AIX and later versions of Mac OS (not 7.6, possibly 8, definitely 9); my only 100Mbit ANS Ethernet card is in the 500. A regular Power Mac-compatible Ethernet PCI card will suffice if all you want to do is run Mac OS.

Let's talk about drivers and PCI devices on Power Macs.

Denizens of the classic Mac OS are painfully familiar with INIT s and CDEV s, which is to say, the extensions and control panels which extend the operating system (and in many cases constitute substantial parts of it). Adding device support to the operating system required a DRVR resource, which could be stored in the declaration ROM of a NuBus card and available at power-on, or in an INIT or CDEV and made available during the boot process, or in a regular application and loaded on demand. (Parenthetically, desk accessories were also implemented as DRVRs.) Even after the 1994 transition to PowerPC, some, if not all, of such code still had to be 68K for backwards compatibility, and thus required emulation on a Power Macintosh.

Since this requirement was an obvious performance bottleneck, Apple attempted to address it in Copland, Apple's fallback attempt to modernise the Mac OS stepwise amid the slow-motion death marches of Taligent and PowerOpen-A/UX 4. Copland's tale of woe is a much longer story, to be the topic of a future article, but the part relevant to this piece was the new driver architecture it introduced. This aspect was part of how Copland's design partitioned its components in memory to avoid the attendant pitfalls inherent in the classic Mac OS. In order to wall the old Mac OS world off but retain compatibility, everything that was 68K code lived in the so-called "cooperative" address space and was treated as data to be interpreted by the Power Mac 68K emulator, including 68K portions of the Toolbox; even PowerPC-native System 7 applications ran here. This cooperative address space would theoretically allow most applications to run as they did before, but intentionally without privileges to the rest of the system nor access to Copland's hardware abstraction layer (HAL).

As such, Copland drivers necessarily were fully native code, in this case implemented as regular PowerPC code fragments. These drivers hooked into the HAL and the Name Registry, an object database that tracked devices on the system and mediated loading and unloading device drivers as needed, and were collapsed into a separate global region at a lower execution level where only limited operating system functionality was available. Although such limitations restricted their ability to integrate with the operating system, it also enabled those drivers to run early in the boot process and remain protected from user code. This new class of driver was called a native driver.

Although Copland suffered from terminal second-system effect just as badly as its contemporaries, it was modular enough for parts of it to be used as transitional enhancements — such as its visual language, which later became the basis of Mac OS 8's Platinum theme, and other pieces that shipped more quietly. Germane to our discussion here was Apple's transition from NuBus to PCI, one not uniformly well-received by users, though in fairness it was effectively forced on Apple when IBM wouldn't support NuBus in the PowerOpen-based AIX 4. For these first PCI Power Macs, starting with the 9500 in 1995, Apple added a port of the Copland Name Registry to their ROMs as well as Eric Traut's faster dynamic recompiling 68K emulator, also intended for Copland.

In this scheme the system ROM initializes the hardware and hands control to its onboard copy of Open Firmware, which creates the device tree for all devices on the system, necessarily including PCI cards but also processor and logic board resources. The Code Fragment Manager, also in the Power Mac ROM, then runs code from any PCI card expansion ROMs and drivers in the Mac ROM itself. This code typically contains a low-level "expert" that creates a node in the Name Registry with sufficient information to identify the device and enable a driver to match against it.

Once the Name Registry is built out, the Mac ROM starts the Display Manager, SCSI Manager and/or ATA Manager, as needed, as part of booting the Mac OS kernel. These Managers in PCI Power Macs implement a different type of "expert" called a family expert. When the MacOS File Manager and Resource Manager are up, the Extensions folder is scanned for native drivers (stored as code fragments with a Type of ndrv, but otherwise the same general structure as their Copland antecessors) and handed to the expert of each particular service category for device classes the family expert supervises. Eligible and matching ndrv s, be they in ROM or on disk, are loaded before any other extension is ever invoked, and the family expert activates and wires them into the operating system.

Apple produced a driver development kit for PCI card vendors that included various debugging tools. This is the Display Name Registry browser from the PCI DDK 3.0, which I got off one of my Apple Developer CDs (there are other tools that do this like @joevt's, whose assistance with certain parts of this project is gratefully acknowledged), showing defined nodes on the ANS 700 booted into Mac OS 9.1 using the 1.1.20.1 pre-production ROM.

The most important thing to notice here is that even though the Name Registry was first added to PCI Power Macs, there are many more nodes here than merely PCI cards, as there would have been in Copland. Both our PCI cards indeed do appear, connected to one of the Bandit PCI controllers (the ANS has two but mapped differently than the 9500, and there is reserved address space for up to four). However, so do things like the CPU, L2 cache, Mac ROM, and devices attached to Grand Central, which acts as a bridge between PCI and traditional Mac devices like the AWACS sound chip (Crystal CS4217 codec), Grand Central's internal SWIM III floppy controller, and the AMD AM79C950KC "Super Combo" CURIO, containing the equivalent of an NCR 53C96 SCSI controller (for the external port), an AMD 85C30 serial chip and an AMD 79C940 Media Access Controller (MACE) for the on-board Ethernet. There are also various nodes that don't correspond to any physical device, such as the ROM software components making up the AIX booter and XCOFF executable loader.

The Display Name Registry browser is interactive and you can drill down into the tree to show a node's properties. I've chosen these two on purpose because they're unique to the Apple Network Server: one of the two NCR 53C825 Fast'n'Wide SCSI-2 controllers, and the Cirrus Logic 54M30 video chip, better known to PC users as the STB Horizon+. These devices are both internally connected via PCI to the first Bandit. Drivers can match on their mandatory name property, which is its primary identifier ( 53c825 and 54m30 respectively), or the optional compatible property generated from the vendor and device IDs.

This first version has three components: two for the Extensions folder, the ANS MACE Fixer, an INIT which patches the Ethernet configuration, and the ANS Video Enabler, an ndrv which allows the 54M30 internal video to be used in 8-bit mode; and for the Startup Items folder, the ANS Startup Fixer, a regular application which rewrites NVRAM to remove inappropriate settings placed there on every boot by the operating system.

The initial piece I put together was the video driver, which is in fact ripped directly out of the 2.0 ANS Mac OS ROM.

Hex Fiend has a rich and extensible Tcl-based template system, including the ability to parse many classic Apple binary formats like resource forks and PEF. Eric Harmon's ROM Fiend extension builds on this by allowing you to parse components of classic Mac ROMs, here a dumped ANS Mac OS ROM provided by our former Apple employee. ROM Fiend splits the ROM into the declaration component and the system ROM ...

... and then allows you to walk the resources within it. This is the video driver embedded in that ROM. Notice the name of the resource is 53m30, which was almost certainly an error.

The actual driver itself is the data portion. The magic sequence Joy!peffpwpc heralds a Preferred Executable Format binary (specifically these three FourCCs indicate an Apple-specific container, that the container is a PEF, and that the architecture is PowerPC) with code fragments. We clip out starting from there ...

... to the end of the data portion and the beginning of the next resource, and emit that section to disk as a separate binary.

All such drivers have a description block, usually heralded by the FourCC mtej (this code seems like it was based on someone's name — spill the beans in the comments if you know). The exact binary format is obscured a bit here by PEF's trivial packing method, used to reduce its footprint in ROM, but note the node name stored as a Pascal string (i.e., length byte first), and then the driver name, also stored as a Pascal string and invariably starting with a dot.

Immediately before the driver name length byte is an $06. The two bits set in this byte indicate that the driver is opened as soon as it is loaded ( kDriverIsOpenedUponLoad, $02), and that the family expert is responsible for doing so ( kDriverIsUnderExpertControl, $04). The PCI DDK documentation states that all video drivers should set these two bits, and only these two. The family expert handling graphics drivers is hinted by the FourCCs in the next line, ndrv for a general native driver service category, and vido for the type, in this case a graphics card.

You might well ask how the production ANS works at all without such an ndrv, and the answer is that Open Firmware doesn't need this driver to display anything on the screen — that's all specifically handled by the code in the ANS ROM, and Harpoon AIX has its own drivers. The ANS was never officially supported with Mac OS, so a proper Mac OS driver was never needed.

To make this extension eligible for loading, we need to fix the file's type code, which must be ndrv ( not INIT), and add a skeletal cfrg resource to tag the single code fragment. The other resources are not strictly speaking essential, but are desirable to give it an icon suite, a version string, and for CCI™, a plain-text description in the Extensions Manager. I created the icons from the ANS template in Hubert Chan's M.A.C. icon pack, which are far better artistic depictions than anything I could ever draw myself in ResEdit.

Although you'll never see a Happy Mac on the internal video when loading this driver from disk, you will see the screen turn on before the usual march of INIT s, because ndrv s load early. (They are also unaffected by holding down SHIFT to load with extensions off, since disabling them could cause the machine to be unusable. Remember that for one of my failures later.) Since we now have two valid displays in this ANS, here is an entire screen grab of both sides simultaneously (the grey boxes is where the identify digits were). Unfortunately the 2.0 ROM driver has the same issue as the AIX driver insofar as none of the chip's 2-D acceleration features are implemented, and the driver only supports 8-bit colour depth even though the chip is capable of much more. This is because the 54M30 provides only a little-endian view into the framebuffer — Apple never wrote anything to byteswap. A project for another day.

Still, the driver otherwise works fine, and we can see that it loaded as a native video driver in TattleTech.

The next thing I started working on was fixing reboots in Mac OS, since every time I shut down the machine I had to reset PRAM or make other changes. This wasn't too hard because I never keep the PRAM battery in it anyway (it's a test machine), but it did mean I had to frequently redo various settings between test runs.

In our previous article in January, we learned this was because Mac OS monkeys with the ANS' NVRAM settings as if it were a real Power Mac 9500, installing an inappropriate nvramrc OpenFirmware startup script that interferes with normal operation, and then sets the input and output devices to serial port ttya, which on the back is serial port 2 (yes, two). On Open Firmware 1.0.5 systems like most beige PCI Power Macs, this does nothing more than keep Open Firmware itself on the serial port; the video and ADB keyboard remain the console. On the ANS' 1.1.x firmware, however, it actually obeys these settings so that you can install and run Harpoon AIX over a serial port, and this was also apparently how Shiner NetWare ran. In this configuration the machine comes up with no video at all, though interestingly ADB devices are still useable in Mac OS, including the keyboard.

The Startup Disk control panel is at least part of this problem. In the CDEV are three resources, OFpt, OFtb and OFtc. The latter two define mappings between the Open Firmware platform identifier and the respective NVRAM settings in OFpt, which is stored as a single long null-terminated string with embedded Mac $0d carriage returns. (The unreleased PowerExpress turns up in this table as the Power Macintosh 9700.) When loaded, the CDEV overwrites the NVRAM settings with the one selected by platform.

Theoretically it should be possible to binary-patch in another mapping and then add a specific script for the ANS, which with this ROM would have a platform string of AAPL,ShinerESB. I determined this approach was unacceptable for two reasons: first, it required modifying standard OS components instead of adding to them, and second, it doesn't solve the ttya problem even if we alter the mapping so that no machines match. In fact, the very string ttya appears nowhere in Startup Disk, suggesting the input and output device settings are being munged someplace else.

In the prior article we solved this issue using Boot Variables, a utility originally written by Paul Mackerras ( now at IBM) which allows you to directly manipulate Open Firmware variables and save them. Because the changes to NVRAM occur before the boot process reaches the Finder, once we get to the Finder we can then fix everything and remain confident it will stay unmolested until the next boot. This process works but obviously requires manual intervention, so since Boot Variables is open source under the GNU Public License, I decided I'd just hack in a hard-coded version which automatically undoes the munge when run.

I converted it to build under CodeWarrior Pro 7 which is my preferred environment for classic Mac work, and rigged it so that it would display a quick window to show you it was working, do its work, and then terminate back to the Finder. When placed in the Startup Items folder, it will do this job every boot automatically, or can be run on demand. If the input device and output device are both ttya, it resets them back to the default kbd (ADB keyboard) and screen (onboard 54M30 video), and installs an nvramrc of its own. The critical code looks like this, using a library function I transplated to do the NVRAM patching in place:

patchstr(21, "kbd");
patchstr(22, "screen");
nvvals[7].word_val = 1; // belt and suspenders approach
patchstr(25,
    "0 to my-self\015"
    "dev /bandit/gc/mace\015"
    "1 encode-int \" PLSCCPort\" property\015"
    "device-end\015"
    "?cr \" Pre-production patches on.\" type\015"
);

The numbers are fixed indexes into NVRAM since this is just a hack, but in order are input-device, output-device, use-nvramrc? and nvramrc itself. This simple nvramrc patches up the Ethernet to work correctly with the Mac OS Apple Enet INIT. Prior Macintoshes with Ethernet, including first generation NuBus Power Macs like the Workgroup Server 9150, had a single Ethernet AAUI port, but AAUI was expensive and unpopular and as the industry moved to twisted-pair Apple offered both an 8P8C ("RJ-45") and AAUI port starting with the 9500 — but still using just the single MACE, so only one port was active at a time. For as yet unexplained reasons, the ANS went back to a single AAUI port with no 8P8C/"RJ-45" despite being an evolution of the same platform base.

This means the MACE is connected directly to the (A)AUI port in the ANS, whereas in machines like the 7300, 7500, 8600, 9500, etc., it switches between the AAUI (equivalent to AUI) or an internal MAU to provide the link over twisted-pair. The MACE embedded in CURIO has a register called PLSCC, or the Physical Layer Signaling Configuration Control, which determines which network port is active. In dual-ported machines, the PLSCC value should be 7 (which includes the $01 enable bit), which corresponds to the "General Purpose Serial Interface" to the circuitry where the signal is routed. In the ANS, however, this value should be 1, which specifies a direct AUI connection.

The ANS Mac OS ROM internally and explicitly specifies a property PLSCCPort on /bandit/gc/mace with that value of 1. @joevt gets credit here (a) for discovering that the Apple Enet INIT looks for and if specified uses this property as an override, relying on a platform default if not, and (b) for the magic incantation required to make this property stick when placed in the nvramrc. Since the ANS looks like a Power Mac 9500 to Mac OS, this value must be provided before Apple Enet runs, so since it's not in the 1.1.20.1 ROM we'll provide it ourselves in Open Firmware before the operating system even starts.

This scheme works and solves both the reboot-shutdown and Ethernet problems simultaneously. But what about bringing the system up from a cold start, where this property won't yet have been set? Well, we have a solution for that too!

The Mac OS NameRegistryLib allows us to directly manipulate the Name Registry (which will necessarily have a copy of our Open Firmware properties), so we can also get this property installed during boot as long as we do so before the Apple Enet INIT opens. We could do this with an ndrv, but we have a simpler and more conventional way which I talked about in this blog before with ways to expand virtual Mac device support in QEMU. kanjitalk755's tablet INIT installs a handler for USB HID devices during startup which allows QEMU absolute pointer positioning to work with its synthesized virtual USB tablet.

In this INIT, a block of 68K code (remember, the normal state of the Power Macintosh nanokernel is to run 68K code in the emulator) invoked at load time displays the icon and uses the Code Fragment Manager to pull a single non-static PowerPC function from the " PPC " resource (yes, P P C and a trailing space), set up a Universal Procedure Pointer to it as PowerPC native code, and run it. This code fragment is what installs the HID report handler.

Because this extension is so modular in design, we can just gut it and replace the PPC resource with our own code (yes, PowerPC code can run from resources, not just from the data fork), though I also manually patched the 68K section with a couple NOP instructions to not bother displaying the icon since we don't really need to. This is the entirety of the PowerPC code:

#include <MacErrors.h>
#include <NameRegistry.h>

// MACE Fixer for Shiner ROM 1.1.20.1
// (C)2026 Cameron Kaiser, all rights reserved
// MIT license
// oldvcr.blogspot.com

#define AIX "Devices:device-tree:packages:aix-boot"
#define MACE "Devices:device-tree:bandit:gc:mace"
#define PLSCCPORT "PLSCCPort"

// Any other function must be declared static!
void main(void) {
	OSErr err;
	RegEntryID regEntryID;

	// Ensure this is an ANS ROM that can boot AIX (2.0 doesn't, but doesn't need this)
	err = RegistryCStrEntryLookup(NULL, AIX, &regEntryID);
	if (err != noErr) {
		return;
	}

	// Find MACE and set the PLSCCPort property on it if not already done.
	err = RegistryCStrEntryLookup(NULL, MACE, &regEntryID);
	if (err == noErr) {
		RegPropertyValueSize s;
		err = RegistryPropertyGetSize(&regEntryID, PLSCCPORT, &s);
		if (err == nrNotFoundErr) { /* may not be found if nvram patches not on */
			UInt32 port = 1;
			err = RegistryPropertyCreate(&regEntryID, PLSCCPORT, &port, sizeof(UInt32));
		}
	}
}

Notice the device tree paths for the two devices we're interested in, Devices:device-tree:packages:aix-boot (or, as an Open Firmware path, /packages/aix-boot) and Devices:device-tree:bandit:gc:mace ( /bandit/gc/mace). We don't need to know anything else about what these nodes are or how they're connected to query and modify them. The first step this function takes is to see if this is an AIX-capable ROM by checking for the AIX booter package as a Name Registry node, and if this package isn't present, such as a regular Power Mac or the ANS Mac OS ROM, then we exit. The second step is to see if the PLSCCPort property already exists; if it does, such as being set from our nvramrc, we exit also, or otherwise set the proper value of 1.

Since the whole scheme can only work if our extension runs first, we give it the special file type of scri instead of INIT, which is notionally a WorldScript extension but can be used to load any sort of extension, because WorldScript extensions load before all other INIT s ( Apple Enet is an INIT). Failing that, the name of the extension ( ANS MACE Fixer) is intentionally chosen to lexically sort above Apple Enet so that it will also run first. The upshot is that the property will be set one way or another before the Ethernet INIT runs, and with this extension installed, now the only circumstance where our Ethernet won't work would be on the very first boot after a PRAM zap with extensions off — which would obviously be an uncommon situation.

It is also important to ensure that main() is the only non-static function in the code fragment because of the way the 68K code finds, declares and calls it (see the prior article for why). CodeWarrior's project settings can be set to build this file as a resource and after doing so we manually merge everything together in ResEdit for the final extension.

As our last stop before the installation instructions, let me also talk a little bit about something not in this version of the extensions pack.

The NCR 53C825 Fast'n'Wide SCSI-2 controller also has its own ndrv in the ANS Mac OS ROM. Indeed, it must, or else the internal SCSI wouldn't be bootable with that ROM (the production and pre-production ROMs have their own support and hand everything over to AIX after boot). It is possible to extract this ndrv and wrap it as an extension in the same way. It won't be bootable, of course, but in theory this should allow devices on the internal SCSI to be used once Mac OS has booted from the external SCSI. Go ahead and try it. It doesn't work. The machine will boot, but no devices are visible from the internal SCSI drive bays.

Apple PCI DDK 3.0 also includes a utility ( Load Driver Test) where you can test the structure of an ndrv to see if it's valid (useful for hardware builders before they spend a lot of money burning defective ROMs). This utility basically checks if the ndrv can be loaded as a code fragment, and if it can, that it has a sensible driver description block, and shows the device node it's looking for and the driver name it installs.

We can immediately see from this that the node name is wrong. In the ANS Mac OS 2.0 ROM, the 53C825 nodes in the Name Registry are named apple53C8xx, not 53c825 as they are in the pre-production ROM. Triumphantly I changed the string and length byte to make the matched name 53c825. It still didn't work.

The PCI DDK has an additional tool ( PCIPeek) which allows you to mess around with PCI-based devices. When we ask it for the PCI configuration space for one of the 53C825s using the node name 53c825, we can pull it up and see all 64 bytes are valid. Though the compatible name doesn't fetch, this does at least prove that the issue isn't the logic board and the node name is correct.

The next step was to look at the driver description in the hex editor. This is again another trivially compressed PEF. Like any well-behaved SCSI driver, it implements a fully-specified SIM (SCSI Interface Module), which, according to the SCSI Common Access Method (CAM), is the link between the 53C825 host bus adapter (HBA) and the transport (XPT) layer that in turn hooks into the SCSI drivers used by the operating system. You should be able to see the device node name and the Macintosh driver name, but the byte before the Pascal string for the Mac driver name here is $04. Unlike video ndrv s, the documentation states SCSI ndrv s should only have a single bit set in that byte, in this case specifying that the family expert handles loading the driver ( kDriverIsUnderExpertControl, $04).

Since that didn't load nor open the driver, I tried setting various bit combinations of forcing it to load upon discovery and/or open upon load, all of which ended up hanging the ANS doing boot. Remember how I said that SHIFT doesn't stop ndrv s from loading? Each of these permutations thus ended up making the external SCSI volume unbootable until the poison ndrv was removed. I had to connect it to the WallStreet PowerBook G3 (it was handy) to get it out, though as a check I had the Wally boot from the same volume just to see what it would do — and it booted fine. The driver doesn't load on the Wally almost certainly because the device name doesn't match anything, which also implies the hang is specific to trying to bring up the device on the ANS or we'd hang on the Wally too.

This leaves us at the mercy of the family expert, so the next thing I tried was various combinations of service category and type. By default this is ndrvgenr, so I tried ndrvscsi, ndrvblok, blokgenr, blokscsi, scsigenr, scsiblok, scsiscsi, blokblok and finally an intemperate combination inappropriate for a family blog, and while none of these locked up the 700, none of them made any difference either.

After all that I'm not sure this approach would have worked for getting the internal SCSI bus working anyway, at least not without additional code. Apple's PCI documentation says, "The SCSI expert is simpler than some other experts" and while it mentions the situation of a "PCI card that wants to register a SIM with the SCSI Manager" which necessarily covers the situation of one in ROM, it says nothing about disk-based drivers. It's possible the SCSI expert just doesn't handle this situation because a non-bootable SCSI bus is certainly less useful, and while we could write up an INIT to try loading the SIM manually, I'm still pondering how this would work and I have yet to find a working disk-based driver for a 53C825-based card that I could hack as an alternative (suggestions solicited in the comments). The PCI DDK 3.0 notably includes a "driver" for this chipset, but only to let you mess around with the hardware — it's intentionally not structured as a SIM, so it wouldn't be an effective foundation.

But you can still try the other pieces, so let's pick up with the install instructions now that you have the prerequisites.

If you were working with a pre-built Mac OS disk image, using the system you used to build it put the ANS MACE Fixer and ANS Video Enabler into the Extensions folder, and the ANS Startup Fixer into the Startup Items folder. If you are doing the install on the ANS itself, simply have the CD disk image ready to go on your external device (or connect a real physical external SCSI CD-ROM).

Assuming you didn't tl;dr this article, your depowered logic board should now be fully reset. Close the drawer and lock the rear key and plug the server back in, then plug in ADB and your SCSI device. Remove all hard drives from the front; you can't boot MacOS from them anyway, and it will simply confuse Open Firmware. The CD-ROM and any tape drives may remain, though do note they currently won't work either. Connect your display to the on-board VGA port, not to any PCI video card, and finally power on the system. If you are using one of Jeff's current replica ROMs, you may need to hit Control-Command-Reset after powering up to get the bong (this is an electrical issue we're sorting out). From a cold start with no bootable AIX volume, the 1.1.20.1 ROM will automatically bomb into Open Firmware, showing you the prompt here. If you don't see this screen, make sure your monitor is connected to the onboard port.

If you've already prepared your external Mac OS volume and the extensions are in their proper places, just type bye at the Open Firmware ok prompt. You will see the message

/AAPL,ROM
MacOS is currently unsupported, use at your own risk.

while the ROM component looks for your startup disk. Once it finds it, there will be a pause, then the screen will flash and drop into the Mac OS mid-boot. Remember, the Startup Fixer must run once every time Mac OS starts up, or your system will come up with a black screen on the next boot. You can manually fix this by entering Open Firmware with a serial connection to Port 2 (38400bps, 8-N-1) and enter setenv input-device kbd, setenv output-device screen, setenv use-nvramrc? false and reset all, or you can just reset the logic board.

If you are doing an install from an external Mac OS CD-ROM or CD image, move your display to the PCI video card and then blindly type bye. You will get the Mac 50% dithered grey, then a Happy Mac, then the CD should start. Install Mac OS as usual to your previously prepared blank disk image. After the installation completes, if you can, install the extensions (e.g., from a floppy disk or via AppleShare over LocalTalk) and startup item as described above before you shut down. Either way, shut down, power off and reset your logic board again, disable or remove the CD-ROM/image, move the display back to the onboard video port, and power back on to the Open Firmware prompt. If the extensions were installed, just type bye — you're good to go. If you couldn't, move the display to the PCI card again, blindly type bye, bring up Mac OS from your external volume, install the extensions, shut down, power off and reset your logic board one last time, then move the display back to the onboard video port. Now you can boot by just typing bye also.

Things still to do:

  • Get the internal SCSI bays working, which may require us to create a modified ROM and put the ndrv there with the proper node name. However, one other possibility is by installing a MacOS-bootable SCSI PCI card. The Shiner logic board has 68-pin connectors on the logic board that directly feed into the two front SCSI busses (bus 0 controls the top four trays and bus 1 controls the bottom three and the 700's rear two). These connectors were intended for the ANS PCI RAID card, but I don't see why we couldn't just connect a regular controller there as long as we change its SCSI ID to not conflict with the 53C825, which should be possible on Adaptec cards with the PowerDomain Control CDEV. I intend to do some experimentation with that, including finding an optimum card which is Mac-bootable (or flashable to same) and supports full Fast'n'Wide SCSI-2, yet is not supported by AIX so that the regular 53C825 will "just work."

  • On a reboot, the ANS may go into its Long RAM Test. This is not only not fatal but is arguably intended behaviour and it will start normally afterwards, though the delay is annoying. On the other hand, even though the ANS Mac OS ROM doesn't do this, it also doesn't properly register the sticks as parity RAM even if they are. I don't know if I can stop the Long RAM Test by tweaking Open Firmware or if it requires a ROM patch, though I suspect it's the latter. In the meantime, you can manually cut it short by hitting Control-Command-Reset.

Hopefully you'll see solutions to one or both of these in a future article. For now, you can get everything on the Github repo, including source code for CodeWarrior Pro 7. Refurb weekend II: Alpha Micro Eagle 300 and friends

2026-10-12, updated: 2026-10-30

This Refurb Weekend is a sequel in two ways.

Six years ago I fixed the power supply and case fan in my 68EC030-based Alpha Microsystems Eagle 300, a more modernized and substantially faster Alpha Micro running AMOS, their unique DEC-inspired multiuser operating system. These blue-collar boxes were very common in many vertical markets due to their tightly integrated business-specific software packages, and are especially unusual for running their big-endian 68000-series processors little-endian (for data file backwards compatibility with their WD-16 ancestors). The 1990s-era Alpha Micro Eagle family improves on the originals with later 68K and even ColdFire CPUs, plus Ethernet and faster SCSI.

The second way it's a sequel is to our previous Alpha Micro refurb weekend, a double header restoring an Alpha Micro AM-1000 and AM-1200, two members of Alpha Micro's most popular series of computers and some of the closest things they made in the early '80s to desktop workstations.

From the outside, the Eagle comes in a PC-style case, but it's not a PC:

This particular Eagle 300, with a 40MHz 68EC030 CPU, runs ampm.floodgap.com using the webserver provided with AlphaTCP — yes, Alpha Micros can be networked — and its own on-board Ethernet. At the time the cooling fan failure was putting a lot of strain on the hard disk because it was overheating, and since this was my first Alpha Micro and I wanted to keep it in good nick, I decided I would put a SCSI2SD in it after the repair and get rid of the spinning disk entirely. Fast-forward to last fall, a little over a year ago, when I tried to do exactly that with a ZuluSCSI.

And then it wouldn't start.

It would power on, but it wouldn't enter the boot sequence, not even with the old hard disk back in it, not even to run the internal self-test. I was worried I'd negligently blown one of its two main system boards and that meant I needed another. This entry took as long as it did to come to fruition because Eagles in general aren't easy to find, and on top of that I was looking for a specific one. Through a couple of referrals I managed to get what I thought was a replacement unit I could raid for parts, but it turned out to be something rather more special — and then I was even more fortunate when I got the Eagle 300 back out of storage to make one last attempt at reviving it.

To cap it off we'll go stick ZuluSCSIs in everybody else, including my Motorola ColdFire-based Eagle 450, the first ColdFire server ever produced and what used to be the fastest Eagle in the house until the new hotness came. I even converted the external BlueSCSI the AM-1200 was using to an internal ZuluSCSI too. Now nearly everybody's got a solid-state boot disk and they're all a good bit more zippy, so we'll gawk at the internals, compare 68K CPU and storage benchmarks and most importantly learn from my mistakes, because as my late father always said, "I'd rather be lucky than good." On a more solemn note, we'll also observe a moment of silence for one of the line's creators who passed away last year. It's time for a Refurb Multi-Weekend Sequel.

Alpha Microsystems, founded in Orange County, California in 1977, produced what were considered some of the earliest "poor man's minicomputers," smaller and more affordable multi-user systems that run a bespoke, Digital Equipment Corporation-influenced operating system named AMOS. In our previous entry we discussed their history in detail. First-generation Alpha Micros like the AM-100, designed by Dick Wilcox who also wrote most of the operating system, used large S-100 cases and a CPU chipset called the WD-16, derived from the Western Digital MCP-1600 chipset — the same one used in DEC's LSI-11 CPU — but with higher performance microcode developed by Rich Notari. These machines thoroughly outclassed low-end PDP-11s yet were substantially cheaper, and Alpha Micro found a ready audience initially with hobbyists and then later corporate turnkey environments, where its integrated AlphaBASIC and database functionality gave it a competitive advantage. As the WD-16 had little elbow room to evolve, in 1982 Alpha Micro introduced new systems based on the Motorola 68000, porting AlphaBASIC and AMOS to run natively, but swapping address lines to make it appear little-endian for compatibility with WD-16 data files and AlphaBASIC P-code. These new machines included the AM-1000, Alpha Micro's most popular single model, and by 1984 it constituted the majority of the over 20,000 Alpha Micro machines then in active use.

An idealized Alpha Micro office from the 1980s might look like this photo, from their actual advertising of the period. The main system is an AM-1042E, the S-100 box sitting on the pedestal next to the printer, using an AM-100/L CPU with an 8MHz 68000 (the same as the AM-1000, which was integrated into a desktop case), and in the factory-standard configuration shipped with 512K of RAM and a 60MB Winchester ST-506 hard disk. The system served some number of local users connected directly via serial ports, in this case the two administrative assistants with AM-60 terminals (a modified and rebadged Wyse WY-100). The fact everyone here was in the same room with the machine was helpful, because AMOS is a strictly real-memory operating system and executable code ran from where it was loaded in the user's fixed memory allocation — there was no memory protection. Although the admin assistants' explicit permissions were limited by which account they were logged into, using the same style of project-programmer numbers as DEC (e.g., [1,2] being the operator account), an errant job of theirs could readily stomp on another and it was not rare for busy systems with buggy software to regularly crash. On the other hand, this also made it fast and efficient with little separation between you and the hardware, and even Alpha Micros with fairly modest specifications could support hundreds of simultaneous users.

Alpha Microsystems tried multiple times to broaden the line technologically, though these efforts were largely for naught. Early attempts to put equivalent hardware onto a PC ISA co-processor card, with software to interchange between MS-DOS and AMOS, yielded only an expensive and poorly-selling PC that wasn't good at either OS (eventually the company gave up producing turnkey systems and just sold the card). In 1984 Alpha Micro introduced UNIMOS, a licensed version of AT&T System V UNIX which ran on modified AM-1000 hardware with an MMU, but it was likewise too expensive and garnered little interest from new users nor demand from existing ones. The cost of its development, the Unix license and its associated royalties, and a simultaneous lawsuit from DEC over AMOS's similarities subsequently caused lasting damage to the company, and by the end of the decade Alpha Micro found itself almost entirely dependent on legacy AMOS users. In the wake of Wilcox's 1990 retirement and original investor Bob Hitchcock's own departure in 1991, new management tried once more with Unix systems based on the Motorola 88000 — which Motorola abandoned shortly afterwards for the PowerPC AIM alliance, and so no hardware ever shipped.

If the platform couldn't be migrated, reasoned Alpha Micro leadership, then it would have to be modernized. A solution was needed for two problems in particular: more up-to-date yet less expensive and fully backwards-compatible hardware for new sales from their risk-averse userbase, and an upgrade path to entice users flatly refusing to part with their old machines. Up to this point, system upgradability had been somewhat uneven and highly model-dependent. RAM and serial port upgrades were generally bespoke boards made from discrete parts which were tedious to replace and repair. Although Alpha Micro had been quick to incorporate Motorola's subsequent 68K CPUs, these higher-performance processors generally only appeared in their larger, more expensive server systems (with the notable exception of the '020, first in the AM-2000 but later in the AM-1600, notionally a desktop computer). Some machines could be upgraded with board swaps, though this wasn't particularly cost-effective, and at the time the most popular AM-1000 and slightly upgraded AM-1200 systems had no official upgrade path from Alpha Micro at all. The December 1987 AM-3000 was the first 68030 machine available from anybody — yes, really, just two months after the '030's October introduction — initially offering a 20MHz CPU, 32K of L2 cache and supporting up to 360 simultaneous terminals, but even the lowliest 30-user configuration started north of $40,000 [about $117,600 in 2026 dollars]. By contrast, Alpha Micro was uncharacteristically tardy in adopting the 68040 and didn't release the 33MHz AM-4000 until 1993. It was nevertheless nearly as expensive, and for most small offices, which were now increasingly Alpha Micro's financial anchor, that kind of money was simply beyond consideration.

In 1993 the company settled on a two-board approach to solve both problems at once. The CPU board, dubbed the Roadrunner and designed by engineer Joshua Stumpf, contained the new processor, standard RAM SIMM slots, L2 cache (if present), and SCSI controller. This board was specifically designed to also fit in legacy machines, specifically the desktop AM-1000, AM-1200 and AM-1600 and server AM-2000 and AM-3000 systems, and initially came in a 68030 and two 68040 versions. A second board served as the CPU board's system interface, linked together using a custom "X-BUS" interconnect over twin 34-pin cables. For legacy installs, this second board was an active interposer physically replacing the original processor, which in elderly units sometimes needed to be desoldered (though that was also true for the few third-party CPU upgrades then extant, like InterLink's Dimension-030, so the Roadrunner was at least no worse). But this second board could be a whole new system architecture of its own, and that was what the I/O board was, designed by Rod Hewitt. It carried the power supply connectors, controlled the system front panel, contained the System Security Device for licensing (more on this later), presented built-in external ports for parallel, SCSI and (for certain loadouts) Ethernet, had an internal port for an optional floppy drive, and provided SIMM-format "paddle card" slots for option cards. Best of all, these boards were smaller and — by using off-the-shelf commodity hardware — cheaper to manufacture, and could be paired into multiple configurations, together becoming the company's long-promised updated low-end and mid-range systems.

In 1994, the new architecture launched — or perhaps I should say took flight, as the Alpha Micro Eagle family. These earliest systems shared a common PC-type minitower deskside case which was also used for a reworked AM-1600LC desktop system and the AM-950 486DX2/66 PC. The central model was the Eagle 300, powered by a 40MHz 68EC030 CPU board (remember, AMOS doesn't need an MMU) and an I/O board with SCSI-2, two parallel ports and Ethernet, plus four paddlecard slots for up to 32 serial ports. The Eagle 400 was correspondingly the same I/O system board with a 33MHz (billed as 66MHz because of the '040's double-speed secondary clock, to be discussed in the second half) full 68040 CPU board and 32K of L2 cache; the Eagle 500 had a 40MHz (80MHz) one. But their best attribute was the price: unlike the big AM systems, these machines started at just a few thousand dollars, depending on license caps, and they'd run all your old software.

If that was still too expensive for you, the company added two more choices that were even cheaper. One was the Eagle 200, which mated the 68EC030 CPU board with a cut-down system board missing Ethernet, one of the parallel ports and two of the paddlecard slots. In November the lowest-end Eagle 100 dispensed with the modularity of the other systems entirely, consolidating the 68EC030 CPU and I/O boards into a single logic board also designed by Hewitt with eight built-in serial ports, no standard Ethernet (offered through a paddlecard upgrade, which I'll show you), only one parallel port and only one paddlecard slot. As promised, Alpha Micro also offered legacy upgrade packages using the same Roadrunner CPU boards, sold separately with their system-specific active interposers for existing installations.

Although collectively the family are called Eagles, the internal designation for the Eagle 300 is the AM-3500-E300 (so the E400 would be the AM-3500-E400, and so forth, reflecting their common ancestry), implying it slotted between their AM-3000 and AM-4000 large systems. The plate sticker also carries the SSD serial number as shipped from the factory, or System Security Device (not to be confused with the modern solid-state drive). In our previous Alpha Micro foray we discussed the SSD's role, a chip installed in every 68K (and later x86) Alpha Micro, even the earliest S-100 boards, used by the operating system and any installed VAR software packages to enforce copy protection and license caps. The SSD number on the rear is just a serial number, printed on the rear plate for convenience and engraved on the SSD chip inside, which I'll show you in a moment. This number is not the key stored inside the chip, up to 256 bytes in length, which only Alpha Micro recorded. When a VAR wanted to lock an install to a particular system, they would provide their private code to Alpha Micro plus the user's SSD serial number, and Alpha Micro would look up the key and generate an alphanumeric PIC (Product Installation Code) that the VAR either used for direct installation or to provide to the user. During the installation process the PIC (usually irreversibly) encoded a binary overlay for the protected executable(s), making it impossible to run them on a system where the SSD didn't match. To facilitate logic board swaps and upgrades, the SSD is socketed and easily transplanted into a new board, but PICs were expensive then and unobtanium now, another reason hard disk backups were so critical.

From top/north to bottom, the ports on the system board are twisted-pair Ethernet (10BaseT), DIP switches for setting the boot device which will become very important later on, an AUI Ethernet port (same NIC as the TP Ethernet, so both cannot be used simultaneously), and two SPP IEEE-1284 ports for parallel printers.

Although Alpha Micros could be networked with the bespoke AlphaNET system and the Eagles were not the first Alpha Micros to have Ethernet, AlphaTCP was developed at the same time as the Eagles, and ran on Ethernet-equipped Eagles as a first-class citizen (AlphaTCP could also be configured to run over SLIP). Next, the internals. Here we have its AM-172 68EC030 CPU board, with a copyright date of 1993, mounted to the bottom of the case in this later unit; early units mounted them vertically on a sidepanel which inconveniently blocked access to the I/O board. In the top left/northwest corner is the SCSI cable, and then the two X-BUS cables. Power is provided by a standard Molex connector stuck in the back betweeen them (remember this detail). On the right/east side is a single SIMM slot containing a 72-pin 16MB parity FPM RAM stick. The AM-172 supports up to 64MB in this slot, though the board needs to be jumpered (at JP5 and JP6) to tell the computer how much is there. There are also various testpoints plus two footprints for what look like alternate (or additional) SCSI connectors.

The three big chips are the 68EC030 processor, which is socketed and has a date code of 12th week 1997, along with an NCR 53C710 SCSI-2 controller (manufactured by Symbios Logic, 2nd week 1997) supporting 10MB/s synchronous transfers, and a Lattice Semiconductor MACH130 PLD (manufactured by AMD, 8th week 1997), basically four "PAL26V16-equivalent" blocks jammed into one die. The CPU and the 53C710 are both clocked by an 80MHz crystal divided down to 40MHz; there are also 16MHz and 50MHz oscillators on the board which appear to be used for the PLD and bus logic.

Likely for cost reasons there is no L2 cache, though another thing to keep in mind is — so I'm told — that for compatibility reasons with 68000 and 68010-era AMOS software it is not possible to enable the data cache (or at least not without substantial difficulty). In fact, we observed exactly this phenomenon when looking at the driver for the InterLink Dimension-030 CPU upgrade, which puts a 68030 in an AM-1000: it never set the data cache bit in the '030's CACR at all. Although some machines can accept an external L2 cache, including one we'll look at in detail, anything it would provide is strictly I-cache.

And here is the AM-319 I/O board (the Eagle 200's cut-down variant was the AM-319-10, the same general architecture with less hardware). The X-BUS cables from the CPU board plus the two AT power connectors from the main power supply are at the upper left/northwest corner. In the upper right/northeast corner are the jumpers and pinheaders going to the front panel. Interestingly there is a set of pads marked SPEAKER between the AT connectors and the front panel connectors, though AMOS doesn't officially support audio. The BR2325 clock battery is hidden under the ribbon for the front panel.

The main chips on the I/O system board are two large Altera PLDs. Although the datasheet says the SRAM storing the logic is backed by either EPROM or Flash, in these first generation Eagle boards Rod Hewitt explained to me that they get completely reprogrammed from the CPU board's boot PROMs on every powerup (adding, "That saved my butt a couple times!"). The PLDs are clocked by a 32MHz crystal in the lower right/southeast corner, and to the right/east of them is the connector for an AM-219 floppy controller, which these systems still supported.

Between the floppy controller connector and the larger PLD sits a small chip in a PLCC socket. This is the SSD (in earlier units it was a DIP; they are functionally identical). Note that all markings except for its engraved serial number have been removed, but people have decapped these, and found that they are otherwise simply specially programmed PALs. There is no known way to read out the code and/or clone it without cracking it open and there was (allegedly) a cottage industry back in the day that did exactly that. It is socketed for easy transfer to a replacement or upgraded system.

To the left/west of the main PLDs are the two unpopulated paddlecard expansion SIMM slots (the other two we'll get to in the next photo). The Eagles inherited this connector from the AM-1600, which was the original system for many of these paddle cards, and has 42 pins so that a RAM stick can't accidentally fit there. Next to the slots is a 3.6864MHz crystal which will tip off some of you as to what the paddlecard slots are normally used for.

If you didn't figure it out, here's one of the paddle cards it came with, an AM-318 8-port serial card. (3.6864MHz is one of those clock speeds that neatly subdivides into standard baud rates and is a hint that there's likely a UART of some kind nearby; see also 4.9152MHz and several other common values.) The two main chips are Philips (now NXP) SC26C94 quad UARTs, each providing four of the eight ports, using a "bidding" system to consolidate and reduce unnecessary service interrupts. AMOS has special acceleration for these QUARTs which Alpha Micro marketed as "Super I/O." Up to 57600bps is supported. The later AM-318-10 uses the refined SC28C94 or SC68C94, but is functionally equivalent in AMOS.

Each card sends off two ribbons to two additional cards installed in the rear (a total of four). These are the 8P8C "RJ-45" ports you saw and are carried on four-port AM-90 "Lightning" boards, consisting of a large array of Zener diodes with one for every active line. As the name implies, they are intended to protect the hardware from high voltage surges on connected terminals, either repelling the excess voltage entirely or limiting damage to the Lightning card itself where the diodes can easily be replaced (there are no other active electronics). In installations with sometimes distant terminals connected by repeater, lightning strikes and other such surges were a non-theoretical risk, so cards like this served as a reasonable insurance policy.

For even larger port concentrations, the AM-318 can directly drive a single RJ-21 Amphenol connector, putting all eight ports on "one" card. Inconveniently the RJ-21 connector requires a breakout cable and is physically identical to a Centronics-style 50-pin SCSI (but is not). I have such an example later on.

Other serial paddlecards can also be installed. The AM-314 provides only four serial ports, but is not merely a cut-down AM-318 — the AM-314 can also be configured for RS-422 (the AM-318 is strictly RS-232) and supports all RS-232 handshake lines (the AM-318 only RTS/CTS), and in certain configurations can trigger a remote reboot from a connected distant console by grounding pin 1 with pin 7. By contrast, the more exotic AM-338 provides an IBM Binary Synchronous Communication "Bisync" link, typically used for Remote Job Entry (RJE) or CICS connections with IBM mainframes, but could theoretically have also worked with some early point-to-point networks like BITNET. It connects to an AM-339 which provides the physical port.

One other possible expansion option comes when we compare those boards with the AM-137 unified board of the Eagle 100. I'm not going to say a whole lot more about the Eagle 100 in this specific article since it's essentially a cost-reduced Eagle 300 with less expansion capability, but because it was so inexpensive to manufacture it ended up outlasting several of its contemporaries. You should be able to identify most of the same landmarks on this one (the SCSI controller, now an LSI part, and the two main system PLDs with stickers on them; the CPU is hidden behind the drive cage and is not visible here) and note that there is only one paddlecard slot next to the single RAM slot. Instead, the E100's serial ports come from an AM-318-10 incorporated into the AM-137 (the QUARTs are in PLCC sockets next to the empty paddlecard slot) and fan out into eight DE-9 ("DB-9") ports mounted directly on the back of the case instead of 8P8C ("RJ-45") ports on cards. These are not regular PC "COM" ports, by the way, and need a passive converter.

The E100 was still capable of Ethernet, though for that you needed an AM-366. These paddlecards were never very common and are now extremely hard to find, and back in the day I ended paying more for the card from an Alpha Micro reseller than I did for the E100 (grrr). It uses a National Semiconductor DP8390D, an ancestor of their later DP83932 SONIC NIC, and is basically a shrunk-down NE1000 card in every other respect. The set of pinheaders at the top is in fact nothing more than a stealth AUI port; the kit came with a mounting bracket and a passive connector cable, but I just connected the cable directly to one of my many AUI transceivers and plugged twisted-pair Ethernet into that. This card is electrically compatible with the other Eagles and theoretically should provide a second interface, but I haven't gotten up the nerve yet to try it. One or both of my E100s may turn up in a future article.

Anyway, back to the work at hand: swap out the E300's SCSI hard disk for a ZuluSCSI. Let's unplug the hard disk and get the bay out.

The rather dusty hard disk, and near as I can tell the original one it shipped with, is a Seagate Hawk ST31051N, a 5400rpm 1GB Fast SCSI drive with a narrow 50-pin interface. Again, because the case was all off-the-shelf PC components, the hard drive likewise sits in an off-the-shelf 5.25"-to-3.5" conversion bracket to which it's bolted, the same sort you'd use for a 3.5" floppy drive in such a bay.

The front drive LED uses standard pinheaders, which we should be able to convert. It looked like someone tried to hotglue the LED cable in position (!) but it was easily convinced to slide off.

I had an old ZuluSCSI RP2040 still on the shelf that I thought would be fast enough for this (note from the future: no, it's not). Using modern emulators like the ZuluSCSI or BlueSCSI for this purpose is helpful because the unit can do the disk copy for you and then store it as a file, making backups as simple as copying the hard disk image file to another computer for safekeeping. Backups are especially critical on systems like these where the operating system is effectively locked to the SSD, and this method of archiving the drive's contents is way easier than tape.

(I should also note for the record that although we're using mostly ZuluSCSIs in this article, I am merely a generally satisfied heavy user, and I have no affiliation or arrangement with their designer other than previously testing some pre-release units.)

Since the ZuluSCSI has no side mounting holes and I didn't have any more plastic enclosures on hand, I used the leftover struts from my SGI Indigo^2 retrofit to see if it could sit on them. It did, so I sheathed them in electrical tape as a "bed," put the ZuluSCSI into initiator mode, connected the old hard disk and the ZuluSCSI to my copy rig, and left it to image the drive to the SD card.

While that was going on, I made the fateful decision to try to clean up the cable rat's nest. As part of this task I rerouted some of the Molex power connectors from the PSU, including the one to the CPU board. When the copy completed I snapped off a couple pin headers from my stack in the parts box and slid them into the LED cable, then connected that to the LED activity vias on ZuluSCSI.

Ready for the power-on test before installing it permanently. It showed a zero on the front LEDs, but it didn't change: the boot sequence wasn't starting. I freaked out, immediately powered it off, and checked everything inside that I'd touched to find I had not properly reconnected the CPU board's power connector.

When I plugged the CPU board back in and turned the system on again, this code ("2d") showed up. I removed the ZuluSCSI and reconnected the Seagate drive. It still showed up. I removed everything from the SCSI bus. It still showed up. Okay, I said to myself in panic, I must somehow have blown the SCSI controller; maybe I can work around it. I held in the reset button while powering it on to see if I could get it into the ROM self-test. The code still showed up.

I powered it down and consulted the documentation. "If status 2d or 3d remains on the display panel, your computer has encountered an error, perhaps due to faulty memory or addressing. Perform 'Procedure #5: Self-Test [which is what I just did].' If your computer does not pass the self test, call your VAR with the information from the test. Stop." Well, that's just dandy. In the list of status codes later on, there is no explicit 2d, just an "xd" where the boot sequence "failed because of a time-out error. This code may indicate faulty memory or an addressing problem." Here the x indicates either the alternate boot device (2), in this case the tape streamer, or the primary boot device (3), in this case the hard disk. The primary and secondary devices are configured by the DIP set on the back, but I hadn't changed those, and even if they needed to be changed for the ZuluSCSI (note from the future: they do), that didn't explain why it wouldn't boot with the original hard disk either.

Given that it couldn't even enter the self-test, there was clearly more wrong than just the SCSI controller. Since it mentioned faulty memory, I did try one of the SGI Indigo²'s 72-pin SIMMs since those are FPM parity also, though I didn't think that was really the problem and as expected it didn't make a difference. It took me a couple hours to calm down because I really like this machine and I'd somehow just killed it doing what should have been a very low-risk upgrade. Sure, I had the E100s and also since acquired a more powerful later model I'll introduce you to momentarily, but this was my original.

I dug up Rod's old E-mail to see if there were any clues in it and recalled what he'd said about the PLDs being dynamically reprogrammed on every startup — from the CPU board. I also knew from the service manual that the X-BUS cables, the only connection between the I/O board and the CPU board, had to be correctly connected or the service manual warned damage could result. A horrible theory stirred in my head: perhaps I had managed to accidentally corrupt the PLDs by effectively bringing up the I/O board without the CPU board, where the boot PROMs used to reprogram them are located. However, that also suggested a solution — there are many undocumented jumpers on the AM-319 and I wondered if one of them could be used to trigger a clean reset of the programmable logic.

I typed out a message to Rod and it bounced, which brings us to the memorial portion of this post: it turned out Rod Hewitt had passed away just months prior, in March 2025. Although Rod hadn't worked for Alpha Micro in some time, he still maintained a few systems as a hobby, and was the developer of the Windows ZTERM terminal package that specifically supported Alpha Micro terminal emulation (Alpha Micro even used it for their AM-80 Windows CE thin client, which might itself appear in a future article). He also had an interest in digital television, developing TSReader, a way to analyse the MPEG-2 transport streams commonly used for satellite, cable and IPTV transmissions.

ZTERM and in particular TSReader became far and away his most popular software packages. However, a few years prior and unbeknownst to many, he had quietly entrusted a copy of the TSReader source code to a friend officially "just in case," and sold ZTERM to MicroSabio, a long-time Alpha Micro support company that maintains A-Shell, a way of running AlphaBASIC applications on modern operating systems. The reason became clear later — he was dying, and it was not treatable. The source code for TSReader was duly posted after his passing and remains today as his most popular legacy. Rest in peace, Rod, and thank you.

Without Rod's guidance, though, there wasn't much more I could think of to do at that point. I unplugged it, pulled the clock battery and let it sit for a couple days to see if that was enough to reset the PLDs, assuming that was the actual problem, and it didn't. It still seemed like it should be repairable if I could only figure out how, but as there was little point in having it sit fruitlessly on the workbench I removed all the remaining cables from the system board and moved the machine to cold storage until I could come up with something else. In the meantime I turned to my alternative system to get ampm.floodgap.com back up and running, though to discuss it we need to bring the history forward some more.

The Eagles were well-received by the user base, though by 1996 it became clear that they couldn't serve the very large installations that were becoming curious about them, and there were just too many models to begin with anyway. The E100 was cheap enough that it sold in good numbers, but few customers fell between it and the E300, making the E200, more expensive to sell and manufacture than the E100, obviously superfluous. Likewise, high-end customers interested in the E500 were interested only in the E500: a junior-varsity 68040, which is what the E400 was, didn't have much appeal. Both the E200 and E400 were quietly dropped.

For large installs that required substantial numbers of serial ports, the existing AM-319 board had to be expanded. The revised AM-319-20 board, providing four built-in serial and parallel ports with a UPS monitor port and a higher-performance DP83902 Ethernet NIC, still had two paddlecard slots, but these slots were widened to 60 pins and could now be part of a bus connected to an external chassis. Alpha Micro had long sold the AM-990, a large capacity case (in this image as used for the AM-4000, though I apologise I don't have a better image of it) and the AM-990 Jumbo, which was even larger. A new higher-performance serial card was developed to take advantage of the widened paddlecard slots, an optically-isolated eight-port card called the AM-359. Twelve AM-359s could be installed in the AM-990, yielding 96 ports when connected to a fan-out in one of the AM-319-20's paddlecard slots (the four on-board ones made an even hundred); the Jumbo could take another twelve AM-359s for another 96 ports connected to the second, a whopping total of 196 serial ports when combined with the base four. If you needed even more, the AM-3501 sidecar chassis could take you well beyond. There was no point in supporting the 68EC030 with such a monster: this new Eagle, officially the Eagle 550 Super Eagle, was 68040 or bust.

For users that didn't want to go that large, a Super Eagle in the standard case could support up to 60 ports, four on the AM-319-20 and then seven AM-359 cards in the usual position. The E550 Super Eagle additionally came as a separate upgrade kit for the E500 and the few E400s that sold, essentially a system board swap, though when sold as a turnkey system it was always with the 40/80MHz CPU. The E550 introduced a new Seiko timekeeper chip as well which not only maintained the time but also the "CMOS settings," the first Alpha Micro with an on-screen setup utility in ROM allowing boot configuration.

Subsequently the company was tardy once again in adopting Motorola's newest 68K CPU, this time the superscalar 68060, which had come out in 1994 aimed squarely at the Intel Pentium but didn't reach Alpha Micro customers until mid-1997. This took two forms, a new 66MHz '060 Roadrunner upgrade option for the E550 Super Eagle and the AM-4000 (lesser Eagles need not apply), and a new AM-6000 large system. Interestingly, the AM-6000 is strongly based on the E550, reflected in its internal designation as the AM-3500-6000 making it a "stealth" Eagle. The '060 Roadrunner not only included the new CPU but also 64K of L2 cache, support for up to 256MB of RAM in four SIMM slots, and 68-pin Fast and Wide SCSI-2 using the NCR 53C770.

In fall 1997 Alpha Micro proudly announced over a thousand Roadrunner '030 systems alone had been sold, mostly E300s, along with E100s and a smattering of E500s and Super Eagles. However, it was not lost on company management that Motorola believed the 68000 family was fast approaching a performance wall. This was made most clear by their then-enthusiastic participation in the PowerPC AIM alliance, but also the rise of ColdFire, which Motorola had first announced in 1994 as well. ColdFire was in its own way Motorola's oblique admission that 68K was losing desktop competitiveness to x86, an attempt to scale the ISA down to embedded markets where its familiarity could be an asset. Approximately 20% of the instruction set such as BCD and certain addressing modes were eliminated, meaning the canonical ColdFire could not be fully binary-compatible with any extant 68K. On the other hand, such cuts enabled the core to execute nearly every remaining instruction in a single clock cycle, and the initial die was a miniscule 4.4mm² at 0.5μm, a third the size of Motorola's own 68300-series CPU32+.

Some amount of this work was done by altering the microcode of the 68040V, a fully static 68LC040. Mindful that ColdFire's incompatibility might impair adoption, Motorola chose to create a bridge first-generation chip from this altered 68040V where omitted user mode instructions were left in, demonstrated on die photos. While the new chip had smaller 2K instruction and 1K data caches than the 68040V, and the MMU was also eliminated, this deviation from spec was still sufficient to run regular 68EC040 code at the user level. Motorola called this first-generation ColdFire chip the MCF5102, produced on a 0.6μm process, and introduced it in 1995 drawing 0.8W at 20MHz and reaching 33MHz. Clock-for-clock there was no way this chip could eclipse an '060, and the emerging "true" ColdFire 520x series couldn't run existing Alpha Micro software, but the MCF5102 was still faster than an '030 and nearly as fast as an '040 — in fact, we'll prove it. On top of that it was cheaper and AMOS didn't need the MMU anyway, making for a plausible mid-range machine that wouldn't imperil (much) sales of the E500 or E550.

In August 1998, Alpha Micro announced their first ColdFire system based on the MCF5102, and near as I can tell was the first ColdFire-based server ever produced. To visually demonstrate its break from the past, the new system got a new, more modern minitower case (also off-the-shelf) with a mix of 5.25" and 3.5" bays but kept the same Eagle badges. Intended to slot between the E300 and E500, it was thus dubbed the Eagle 450.

Although Rod Hewitt was no longer working full time for Alpha Micro by then, he still had enough of a relationship with the company that they lent him a pre-production model for evaluation, which he received with enthusiasm. He was generally complimentary in his public review to alt.sys.alpha-micro, though credit must be given to John F. G. Leighton, then Alpha Micro's VAR marketing manager, who chose to print the review unedited in marketing materials, even Rod's gentle complaints. Since this is the only E450 I have personally laid my hands on, we will be referring to his comments liberally as a point of comparison, and consequently the E450's history is probably the best documented of any 68K Eagle. It rolled out to users in October at the annual meeting in nearby Riverside, California.

This particular system was a gift from someone who inherited it from an 9-1-1 emergency dispatch centre and wanted to find it a good home, another way that running an Alpha Micro-powered web server has paid off. I was able to quickly get into the system (if it's not clear by now, I love hacking into Alpha Micros) and reconfigure it, and it had lurked as the E300's work spare and a test unit since then. Like the E300 it has a bootable tape drive, but this time it's a more modern DDS/DAT.

The E450's new case became the standard for subsequent systems (my E100s are both in this case) but still has the same basic rear layout with eight cutouts for each bank of serial ports, albeit slightly rearranged. Some aspects of the system, like the on-board UPS monitoring port, were derived from the E550 as was the same Seiko timekeeper chip, improved Ethernet NIC, and on-screen "CMOS setup" tool in ROM. On the other hand, its NCR 53C770 Fast and Wide SCSI-2 controller came from the '060 Roadrunner, and the system has but one parallel port and only twisted-pair Ethernet (no AUI). Take note of the pop-out panel just above/north of the RJ-45 Ethernet jack; I will comment on this specifically later. I don't know what the handwritten "#8218" means.

Two fans run at the top, one in the AT supply plus a case fan; just below/south of the case fan is the 68-pin external SCSI connector. There are some shenanigans with this particular unit's documentation and internals, to be demonstrated as well, and I've long wondered if this was some sort of test model (the donor did not know). In particular, the serial number of "9999" on the backplate is clearly bogus, the model number should be AM-3500- E 450, and it claims not to have an SSD at all (untrue). As such, I'm not sure I can believe the stated manufacturing date of September 2002, and at least one date inside directly contradicts it. It's possible this was a case with a transplanted board.

The E450 is another unified board called the AM-138. Alpha Micro made upgrade kits (again, basically board swaps) for the AM-1600, E100, E300 and E500 that replaced their internal components with this one. The internal SCSI cable can be seen going from the rear port to the DDS tape drive and hard disk ...

... and then to the AM-138, covering up the 53C770 controller behind it. There are two SCSI connectors on the logic board, but not two busses, and they can't be used at the same time. The top 50-pin one is meant for when all you have are narrow devices; the bottom 68-pin one is the higher-performance wide connector, though the SCSI bus on this machine is finicky about what it will talk to. As the AM-138 no longer supports the older AM-219 floppy controller, an optional SCSI floppy disk drive was made available as a substitute.

Although you can see three paddlecard connectors which are compatible with the same AM-314 and AM-318 serial cards, the E450 embeds an SC28C94-based AM-318-10 with Super I/O into its own board similar to the E100. Each four port half goes to its own AM-90 Lightning board to total our eight serial ports. The 3.6864MHz serial clock crystal can just be seen peeping out from behind the rear board in this view.

This is the replacement timekeeper, a Seiko Epson RTC65271. You can pry the BR1225 batteries out of it and replace them far more easily than any dead Dallas timekeeper. Also visible is the SSD in its usual PLCC socket, to the southeast/lower right, and the first of several unpopulated regions on this board, the AUI connector at J3 to the northwest/upper left.

Several more glaringly unpopulated areas are apparent despite a board copyright date of June 2001 (top left/northwest corner, next to the AT power connectors), well after the E450's ostensible introduction. The major one is labeled "PCI," at J6 and J5, kitty-corner to the DP83902VF NIC at U15. That is indeed per Rod's summation where two PCI slots were supposed to go, along with their IDT CA91C860 68K host-to-PCI bridge chip on the empty pads near the centre of the image. The PCI era arrived during the 68K architecture's market decline, making PCI slots unusual in any 68K system, and the manual for the E450 says the PCI slots were "[n]ot supported in initial release" consistent with Rod's observation that the regions were taped over.

However, Alpha Micro was already advertising E450 systems with PCI slots in 1999 as prerequisites for the AM-370, an unidentified off-the-shelf 100Mbit PCI NIC that goes into the "slot" at J5. To access these PCI slots, that rear panel I pointed out needs to be removed. The AM-370's availability implies all shipping E450s should have had them by then — there was even an alleged board-swap program to do so. I've yet to find another one, so I don't know if that's true, but it would be interesting to find out because with this card or the OEM equivalent you would have two fully operational NICs and multihoming was reportedly supported. I also don't know what's going on with the unpopulated "option connector" at P5 to the right/east of the AT power connectors.

At least there are connectors for the other slots. The E450 is one of only a few Alpha Micro systems that can accept an optional external L2 cache, though as mentioned this cache is only enabled for instructions, and the form factor does not match any PC cache stick — in fact, it's the same as a 72-pin SIMM, so don't put the wrong one in the wrong place (Rod also objected to this). The only size supported is 64K, the same cache stick used for the AM-6000 and the '060 Roadrunner, part #PDB-00701-00. I've never seen this cache stick and comparison of his numbers with my cacheless E450 suggests it only yields around a fourteen percent boost, not nothing but not much, likely because it can't do anything for the data cache (though stand by for a very important observation on actual clock speed).

The E450 also has two 72-pin SIMM slots, which need not be paired and support up to 256MB, though as with the earlier systems the machine needs to be jumpered to tell it how much is there. The tag on the one in J11 (service order 13009, apparently) is dated January 18, 2002: that makes this machine at least eight months older than its alleged manufacturing date, and to have received an upgrade suggests it's even older than that. Between the two sticks this system has 72MB of RAM. Below/south of the RAM SIMMs are the three paddlecard slots.

Also in this image is another obvious non-populated area: a pin-grid array marked "PGA040" at U89 in the northeast/upper right hand corner. That sounds like somewhere the CPU would go, and the footprint looks like an '040. So where's the actual processor?

The ColdFire MCF5102 is in fact hidden behind the drive bays, the only chip with a heatsink, which should tell you it's doing an awful lot of work. How fast is it doing it, though? While Rod's review stated his prerelease system was apparently running at 33MHz, the oscillator closest to the CPU can be seen clearly in this photograph, and it's ... 25MHz. There are no other crystals on the board except for the serial port one you saw earlier, the official marketing announcement has a board layout that also clearly labels this crystal as 25MHz, and nothing in the MCF5102 user's manual says the chip does anything tricky with the clock. As it happens, the only place in Alpha Micro documentation where the E450's CPU speed is given is Rod's review: everywhere else, even the data sheet, simply says it's a ColdFire and nothing more. Since mine is only 14% slower than his, and his had the cache, his can't possibly have been running at 33MHz either. The E450 is a 25MHz ColdFire, full stop.

In a backwards way, however, this is nothing less than validation of how performant early ColdFires could be. Recall that our E300, a 40MHz 68EC030, had a "CX" computing index score on the SI.LIT benchmark of 36.9. The same benchmark on this E450 with a 25MHz MCF5102 gets a score of 59.9, and Rod's with 64K L2 came in at a whopping 68 (Alpha Micro said 68.5; either one is around 14% higher). By contrast, the E550 Super Eagle, with a full 40MHz ("80MHz") 68040 Roadrunner clocked 60% faster and 32K of L2 cache, officially gets ... 79.9 (note from the future: my figure is 83.6) — the full cached-up faster-clocked 68040's performance on the same code is only around 33-40% better, and just 16-22% or so if the E450 has its cache too. Put another way, the CX/MHz ratio of the faster 68040 was right around 2.0, while the CX/MHz ratio of the MCF5102 is 2.4 without the cache, and almost 2.75 with it.

Likely because the lower clock speed would have looked bad in marketing materials, similar to why General Magic never mentioned the clock speed of the DataRover 840, Alpha Micro simply chose not to mention it either. Still, this machine's surprising efficiency proves ColdFire, at least early on, definitely had legs. I'm not sure how Rod got it wrong except that an earlier version may indeed have run that part, though with these numbers, if there had ever been a production 33MHz E450 it might have seriously endangered sales of Alpha Micro's remaining '040s — perhaps that's why they didn't use it even though the faster part existed. Best guess is that the AM-138 was originally designed for the 68040 and then quickly retrofitted for ColdFire, leaving the PGA region as an "R&D test point" (as documented).

Because of all those serial ports I expected a lot more cabling coming off the AM-319 system board, and indeed there was. But what I didn't expect was the CPU board on the bottom: it's a full 68040, just like the test said.

This is the faster of the two AM-174 CPU boards, the '040 boards for the original two-piece Eagles I mentioned earlier. Although Alpha Micro eagerly billed this AM-174-02 as having an "80MHz" 68040, that sort of marketing is deliberately simplistic. Recall that 68040s take two clock signals, one labeled Bclk for the bus clock, and then a second exactly twice as fast labeled Pclk as the so-called processor clock. In the 68020 and 68030, which accept a single clock signal, their internal ALU runs at only half the bus speed such that the 40MHz 68EC030 in the Eagle 300 actually has an ALU running at just 20MHz. For the 68040 Motorola removed this limitation to run its ALU at full bus speed, but the chip designers also studied trace data to optimize for the most common instructions, implementing a 7-stage pipeline where most effective address calculations and fetches occur with no penalty. The upshot of this was to cut most instructions' cycle count in half or more.

The 2x processor clock is truly used, but not to speed up the ALU, so it's wrong to say the 68040 is "double-clocked." In a two-part 1990 article in IEEE Micro, Motorola explains that "Pclk provides timing reference points within each Bclk period," employing it for synchronous sub-cycle timing, and furthermore explicitly states that "all internal operations cycle at the Bclk rate." Still, the fact this clock signal was present at all gave Apple an excuse to tout both timings for '040 Macintoshes, and Alpha Micro cheerfully reported just the faster one, even though the chip only appears to run at that comparative speed from its larger 4K L1 cache, unhindered ALU and reduced cycles per instruction.

On this board, Pclk is provided by the same 80MHz crystal we saw on the AM-172, divided down by two to yield Bclk in the same way the 68EC030 board does for its single 40MHz clock. (For the E400's AM-174-00, this crystal would have been 66MHz divided down to 33MHz.) The single parity FPM SIMM slot and 16MHz and 50MHz oscillators are also present, as well as the same 53C710 SCSI controller, here a genuine NCR part. However, new for this board is 32K of L2 cache at the upper right/northeast corner, implemented with two IDT 71B74 8K cache-tag RAMs together providing 29 bits (512MB) of address comparison, and then four Cypress CY78C185 8K SRAMs for the cache itself. Remember, however, that in AMOS all cache is I-cache.

Effectively this 40/80MHz AM-174 makes our new system a full Eagle 500, so why is it labeled as "only" an E300? I don't how how these systems originally shipped from the factory nor whether the E500 designation actually appeared on the back, but Alpha Micro did run a promotion in late 1997 where you could upgrade any Roadrunner '030 to a Roadrunner '040 by swapping the CPU board. My guess is this is one of those systems, and because that upgrade kit wouldn't have changed the plate on the back itself, the reseller simply noted it to be a working E300 and sold it to me as such. I dragged the ailing hulk of the E300, now sans hard disk, back out of climate-controlled storage. By this time it had sat with no power and no clock battery for over eight months.

The plan was to transplant the AM-319 and AM-174-02 as a matched pair from the "secret" E500 into the nicer case of the E300. Before committing to surgery, and leaving its hard disk still out, I reconnected the E300's system board to give it one more chance to start. Checking all my connections thoroughly, I then plugged it into the power strip and turned it on, expecting to see the dreaded 2d code again.

It tried to boot.

Startled, I powered it off, connected the everything console, and turned it back on with the reset button held in to force a self-test. Except for the missing hard disk, it passed the self-test — even the SCSI controller tested good.

I decided to push my luck and connect the ZuluSCSI, and this time it did throw a 2d. I freaked out again, powered it off, let it sit and then gingerly turned it back on. It still did it. However, when I disconnected the ZuluSCSI, it went back to trying to boot, and a repeated self-test was still clean.

This was clearly new behaviour — beforehand, it wouldn't do anything, not even enter the self-test, let alone attempt booting. Recall that error 2d had two mentions in the manual, the second one referencing the primary and secondary boot devices. Since the self-test said the SCSI controller was fine, this made me suspicious that there was something about the ZuluSCSI's configuration the machine didn't like. Knowing some systems can get finicky about sluggish devices immediately after power-up, I reconnected the ZuluSCSI and powered the E300 back on. Code 2d duly appeared, but this time instead of turning it off, I hit the reset button just to see what it would do.

It booted. I checked out the system and the files and jobs I knew should be there, and everything seemed to be operating normally, just as it used to. Here you can see all three panel LEDs lit (power, CPU activity and disk activity) along with the LED for the drive bay. Resetting it again, it booted cleanly a second time. I could find no other defects; it seemed fully functional.

I was delighted it had somehow revived itself in hibernation, but I'm not willing to do much digging into its Lazarus act. The only thing I can think of is that the prolonged de-energised period either completely reset the PLDs, as I hoped would happen, or glitched them enough to force a reload anyway. That's obviously not a theory I'd like to test. In support of said theory, however, although I got the same abnormal front panel code each time, the root cause on each occasion seemed different. Beforehand, it was something about the connection between the system board and the CPU board. Now it appeared to be the SCSI bus.

The other problem is that the boot didn't seem appreciably faster. In fact, the hard disk score from SI.LIT had actually dropped to around 10, which was 33% slower than its original hard disk.

Debug mode obviously substantially impacts SCSI throughput because now the processor in the ZuluSCSI has to emit serial debugging information while it's satisfying requests, but SCSI activity during the first run didn't seem unusual. On the other hand, the activity during the second run was very unusual: there wasn't any. In fact, even though the baseline score had sunk down to a dismal 10 or so because of all the debugging data it was emitting, the second run was still a blistering 180.7.

This really sounded like operating system caching, but except for the AM-1200 where I wasn't running it to save memory, the other three systems were running the standard disk cache as virtually any performance Alpha Micro would — and allegedly SI.LIT should be unswayed by it. For some reason the E450's cache configuration wasn't locking UFDs (user file directories, i.e., PPNs), but turning that off on the E500 and E300 didn't make a difference, and all three were caching everything else including the MFD (master file directory). However, when I turned off caching altogether at runtime (using the CACHE.LIT tool and disabling with OFF), though the scores got really low, they were now consistent from run to run.

Do note our observation isn't enough to fully explain the E450, which also runs the OS disk cache, but didn't have a second run bump. If you disable the cache on the E450, although its overall score declines, it still remains consistent from run to run. One possibility is that the driver for its later SCSI controller just isn't as aggressive.

Although the overall issue certainly calls into question how useful SI.LIT is as a disk benchmark, despite being likely the only Alpha Micro benchmark tool you can expect most recent systems to come with, the question then becomes how comparative disk performance on an Alpha Micro should be measured. Was it still fine for me to continue with my usual practice of leaving the cache on and testing immediately after boot? It's probable that there'd be little in the cache by that point, whatever would be there would likely be similar from system to system (assuming the same version of the operating system), and likelier still that whatever was present in the cache wouldn't be very germane to SI.LIT. Under my current knowledge of AMOS I think these numbers are still broadly comparable; I just have to keep in mind that the score on subsequent runs is likely to be bogus.

With our Alpha Micro stack now in operation, shown here from the E300's console as it continues serving the world as it did before, let's briefly finish the story of the Eagles. The E100 and E450 became the basis for a number of even smaller systems used as network servers (e.g., the E100NX with few, if any, directly attached terminals) fed by network-connected terminal servers (e.g., E100TX, E450TX) based on the same platform. The single board systems were much cheaper to manufacture, and Alpha Micro discontinued the E300, E500 and E550 in 2000 to introduce the MCF5102-based E250, a cost-reduced E450 in the same way the E100 was a cost-reduced E300, running exactly the same processor at the same speed (Alpha Micro themselves reported a CX score of 59.9, precisely even with our E450 here). The E100 was discontinued shortly afterwards in 2001.

For Alpha Micro, the end of their 68K architecture systems was ultimately tied to the end of the 68K architecture generally. Motorola had never planned to evolve the MCF5102 further as it was always meant as a stopgap, and later ColdFires were not sufficiently suitable nor compatible to run the software legacy AMOS users ran. Although Alpha Micro's Falcon line of PC compatibility cards used them as a CPU starting with the 2002 PCI SuperFalcon (AM-113), it soon became clear PCs were fast enough for software emulation to be a far more effective option. In 2003 Alpha Micro introduced the AM-8000, an AMD Athlon PC running Windows XP Embedded with an on-board SuperFalcon, but here the SuperFalcon was demoted to a coprocessor for handling the SSD and terminal I/O running a reduced "Embedded AMOS" monitor. Everything else was an efficient software emulation, yielding a SI.LIT CX score of 816 (!) on dual Athlon 2800+ CPUs. Later AM-113 SuperFalcons were just serial ports and a socket for the SSD; the main system was now more than suitable to service them, and Motorola wasn't making any more 5102 CPUs either. The Eagle 800 that same year ran the same technology in miniature, bringing the great experiment to a close with the discontinuation of the last E250 and E450 systems, and today's systems sold by the reformulated Alpha Microsystems LLC use the same x86-based architecture.

Over their production lifetime, analysis of known serial numbers suggests around ten thousand 68K Eagles were ultimately sold, and now I've got five of them. Rest in peace, Rod. They're still great machines.
